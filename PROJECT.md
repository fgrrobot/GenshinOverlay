## 1. Краткое резюме

**Teyvat Lens** — настольное приложение для Windows, работающее поверх игры **Genshin Impact**
как прозрачный оверлей.

**Проблема.** В игре есть открытый мир с сотнями сундуков и ресурсов, но игра не показывает, что
находится рядом: на внутриигровой миникарте есть только телепорты, статуи, домены и метки игрока.
Игрок, который хочет зачистить локацию на 100%, вынужден держать открытой интерактивную карту в
браузере, вручную отмечать собранное и постоянно переключаться между окнами. Встроенный игровой
компас (гаджет «Компас искателя сокровищ») показывает только направление, имеет перезарядку и
не покрывает все типы объектов.

**Решение.** Приложение:

1. Захватывает изображение окна игры.
2. Определяет положение игрока в мире по внутриигровой миникарте (визуальная локализация).
3. Сопоставляет координаты с локальной базой маркеров (сундуки, ресурсы, точки интереса).
4. Рисует поверх игры собственную мини-карту с объектами вокруг и указатель на ближайший объект
   с расстоянием в метрах.

**Ключевое ограничение.** Приложение работает строго в режиме **read-only**: не внедряется в процесс
игры, не перехватывает графический API, не читает память, не эмулирует ввод. Взаимодействие с игрой
ограничено двумя каналами — захват экрана и отдельное прозрачное окно.

**Платформа:** Windows 10 1903+ / Windows 11, x64.
**Стек:** C# 12 / .NET 8, Windows Graphics Capture, OpenCV, SkiaSharp + DirectComposition, SQLite.

**Ключевые числа (цели):** точность позиции — медиана ≤ 3 м, p95 ≤ 8 м; оверлей — 60 FPS;
дополнительная нагрузка на GPU ≤ 5%; RAM ≤ 300 МБ; задержка «мир → пиксель» ≤ 150 мс.

## 2. Домен: что такое Genshin Impact в контексте задачи

Чтобы документ был понятен без знания игры, ниже минимум необходимого контекста.

**Genshin Impact** — игра с открытым миром от HoYoverse. Мир состоит из регионов (Мондштадт, Ли Юэ,
Инадзума, Сумеру, Фонтейн и др.), между которыми перемещаются телепортацией. Мир трёхмерный, но для
карты и навигации достаточно плоскости: горизонтальные координаты далее обозначаются **X** и **Z**,
вертикаль — **Y** (используется только для подсказки «объект выше/ниже»).

**Сундуки** — объекты, которые игрок открывает ради награды. Имеют категории (обычный, изысканный,
драгоценный, роскошный, «примечательный»). **Сундуки не отображаются на внутриигровой миникарте.**

**Ресурсы** — растения, руда, грибы, рыба, кристаллы и т. п. Часть из них возрождается через
фиксированное время (обычно 48 или 72 часа реального времени). ⚠️ Допущение: конкретные интервалы
зависят от типа ресурса и должны быть уточнены по внешним источникам при наполнении базы.

**Внутриигровая миникарта** — круглый элемент интерфейса фиксированного размера в углу экрана.
Показывает рельеф, телепорты, статуи, домены и пользовательские метки. Масштаб фиксирован.
⚠️ **Ключевое неизвестное:** вращается ли миникарта вместе с камерой или всегда ориентирована на
север. От ответа зависит алгоритм оценки угла (§8.3). Это первый вопрос, который нужно закрыть
перед реализацией.

**UI игры** может скрываться (режим фото, катсцены), миникарта может перекрываться элементами
интерфейса (щит, баффы, квестовые маркеры). Это влияет на устойчивость распознавания.

**Правила игры** запрещают сторонний софт, взаимодействующий с клиентом. Поэтому проект
сознательно не делает ничего, что можно трактовать как вмешательство (§10.6).

## 3. Продукт: что именно делает программа

### 3.1 Основные функции первой версии (MVP)

1. **Захват окна игры** в режиме borderless windowed.
2. **Автоматическое определение позиции игрока** по миникарте, с оценкой уверенности.
3. **Калибровка** под конкретное разрешение экрана и масштаб интерфейса.
4. **Локальная база** сундуков и 5–8 категорий ресурсов.
5. **Оверлей-миникарта**: карта вокруг игрока + иконки объектов в радиусе.
6. **Указатель на ближайший объект** с расстоянием и подсказкой о разнице высот.
7. **Корректное поведение окна**: прозрачность, сквозные клики, поверх всех окон, отсутствие в захвате.
8. **Горячая клавиша** показа/скрытия оверлея.
9. **Честная индикация состояния**: `Tracking` / `Degraded` / `Lost`. При потере позиции оверлей
   не показывает правдоподобно выглядящую, но неверную информацию.
10. **Трей, настройки, сохранение состояния** между запусками.

### 3.2 Пользовательские сценарии

**Сценарий A. Зачистка региона.**
Игрок выбирает регион, который хочет зачистить. Программа отображает все несобранные сундуки
вокруг и указывает ближайший. Результат: игрок знает, куда идти, и не пропускает объекты.

**Сценарий B. Прокачка персонажа.**
Игрок выбирает персонажа. Программа определяет, какие ресурсы нужны для возвышения, и показывает,
где они находятся. Результат: маршрут сбора ресурсов.

**Сценарий C. Поиск артефакта/предмета.**
Игрок выбирает предмет. Программа показывает места, где его можно получить.

### 3.3 Границы: что в продукт НЕ входит

- Автоматизация действий, автопути, кликеры, любая эмуляция ввода.
- Чтение памяти игры, инъекция DLL, хукинг DirectX.
- Подземелья и многослойные регионы в первой версии.
- Распознавание объектов нейросетью в первой версии (база координат точнее и дешевле).
- Мобильные платформы, консоли, macOS, Linux.
- Сетевая синхронизация, аккаунты, облако.

### 3.4 Отличие от существующих решений

| Решение | Что даёт | Чего не даёт |
|---|---|---|
| Интерактивная карта в браузере | все объекты, отметки | не встроена в игру; нужно переключаться; нет привязки к позиции игрока |
| Игровой компас (гаджет) | направление на ближайший сундук | перезарядка, ограниченный радиус, не все типы объектов |
| Читы | всё | нарушение правил, риск блокировки аккаунта |
| **Teyvat Lens** | позиция + объекты + overlay | требует borderless-режима; зависит от качества локализации |

## 4. Ключевая техническая идея

Игра **не предоставляет** координаты игрока: нет ни API, ни отображаемых координат, ни файла
сохранения с позицией в удобном виде. Поэтому позиция **вычисляется из изображения миникарты** —
это центральная идея проекта.

Схема рассуждения:

1. Миникарта показывает участок мира вокруг игрока с фиксированным масштабом.
2. Если известен масштаб (пикселей на метр) и угол поворота, то смещение картинки миникарты
   между кадрами = смещение игрока в мире.
3. Если дополнительно сопоставить видимый фрагмент с полным атласом карты, можно получить
   **абсолютную** позицию, а не только относительное смещение.

Отсюда три независимых источника позиции, которые работают одновременно:

- **Одометрия** (относительная, быстрая, 15 Гц) — по смещению между соседними кадрами.
- **Релокализация** (абсолютная, медленная, 1 раз в 1–3 с) — сопоставление с атласом карты.
- **Слияние** — фильтр Калмана объединяет оба источника и даёт итоговую позицию с уверенностью.

Одометрия даёт гладкость и мгновенную реакцию, но накапливает дрейф. Релокализация даёт абсолютную
привязку, но работает редко и может ошибаться. Вместе они дают и точность, и стабильность.

Второй ключевой факт: **сундуки и ресурсы берутся из базы, а не с экрана.** Поэтому база координат
является полноценной частью продукта, а не вспомогательной.

## 5. Архитектура: общая картина

### 5.1 Два процесса

```
┌──────────────────────── Core.Host (процесс 1) ─────────────────────────┐
│  захват экрана, компьютерное зрение, локализация, опциональная детекция │
└───────────────────────────────┬────────────────────────────────────────┘
                                │ shared memory + MessagePack
                                │ (атомарный снимок состояния)
┌───────────────────────────────▼────────────────────────────────────────┐
│  Overlay.App (процесс 2): прозрачное окно, отрисовка, настройки, трей   │
└────────────────────────────────────────────────────────────────────────┘
```

Почему два процесса:

- падение модуля зрения не должно закрывать оверлей и наоборот;
- модуль зрения можно заменить (например, прототипом на Python) без переписывания UI;
- проще изолировать потребление памяти и приоритеты потоков.

Обмен — через разделяемую память: писатель публикует **готовый снимок состояния целиком** вместе
с номером последовательности, читатель берёт последний. Никаких блокировок в горячем пути.

### 5.2 Три контура с разной частотой

| Контур | Частота | Где считается | Зачем такая частота |
|---|---|---|---|
| Захват кадра | 30–60 Гц | GPU | дешевле, чем кажется; нужен свежий кадр |
| Анализ изображения + локализация | 10–15 Гц | CPU (+GPU) | дорого; позиция меняется медленно |
| Отрисовка оверлея | 60 Гц | GPU | иначе интерфейс выглядит рваным |

Между контурами — **интерполяция и экстраполяция по времени**: позиция обновляется 15 раз в секунду,
а рисуется 60. Это обязательное условие плавности: без интерполяции стрелка будет дёргаться.

### 5.3 Поток данных

```
окно игры
   │  Windows Graphics Capture (GPU-текстура)
   ▼
кольцевой буфер кадров (2 слота, «побеждает последний»)
   │  уменьшение до 640×640 на GPU, один перенос в память
   ▼
Vision.Minimap: поиск круга → кроп → grayscale → CLAHE → маска HUD → оценка угла
   │  MinimapPatch
   ▼
Localization.Engine: одометрия (phase correlation) + релокализация (ORB/RANSAC) + фильтр Калмана
   │  GeoState {X, Z, Y, layer, heading, confidence, timestamp}
   ▼
Query.Engine: поиск в SQLite через R-дерево → маркеры в радиусе
   ▼
Navigation.Hints: выбор цели, азимут, расстояние, разница высот
   │  Scene (список иконок + указатель)
   ▼
Overlay.Presenter: интерполяция → SkiaSharp → DirectComposition → экран
```

### 5.5 Контракты между модулями

```csharp
public readonly record struct MinimapPatch(
    ReadOnlyMemory<byte> Gray,   // нормализованный кроп 256×256, 8 бит
    Point2 CenterPx,             // центр круга в координатах кадра
    float RadiusPx,
    float HeadingDeg,            // направление камеры, 0 = север
    bool HeadingValid,
    long TimestampMs,
    float Quality);              // 0..1

public readonly record struct GeoState(
    double X, double Z, double? Y,
    int LayerId,                 // 0 = поверхность
    float HeadingDeg,
    float Confidence,            // 0..1
    float AccuracyM,             // оценка погрешности позиции, ±м
    LocalizationSource Source,   // Odometry | Relocalized | Manual
    long TimestampMs,
    string? RegionCode);

public sealed record Marker(
    long Id, MarkerKind Kind, string? Subtype,
    double X, double Z, double? Y, int LayerId,
    double DistanceM, double BearingDeg,
    bool Collected, DateTimeOffset? RespawnAt);
```

Правило: состояние публикуется неизменяемым снимком с номером версии. Никакой модуль не читает
внутренние поля другого напрямую.

### 5.6 Режимы работы

| Режим | Условие | Анализ | Что видит игрок |
|---|---|---|---|
| `Idle` | игра не в фокусе | 0 Гц | ничего |
| `Tracking` | уверенность > 0.7 | 15 Гц | полный оверлей |
| `Degraded` | 0.4 < уверенность ≤ 0.7 | 15 Гц + форс релокализации | оверлей + индикатор уточнения |
| `Lost` | уверенность ≤ 0.4 дольше 2 с | 5 Гц, только релокализация | сообщение «позиция неизвестна» |
| `Suspended` | хоткей / окно свёрнуто | 0 Гц | ничего |

Переходы — автомат состояний. Важно: **`Lost` — это нормальное состояние**, а не ошибка. Показывать
неверную позицию хуже, чем не показывать ничего.

### 5.7 Бюджеты производительности

| Участок | Бюджет |
|---|---|
| захват → готовый кадр | ≤ 2 кадра задержки |
| кроп + поиск круга + поворот | ≤ 2 мс |
| phase correlation | ≤ 1 мс |
| Калман | ≤ 0.1 мс |
| релокализация (раз в 1–3 с, в фоне) | ≤ 25 мс |
| запрос к базе + подсказки | ≤ 1 мс |
| отрисовка кадра | ≤ 3 мс CPU / ≤ 1 мс GPU |
| **итого «мир → пиксель»** | **≤ 150 мс** |

| Модели ONNX (позже) | по версии | файлы | 6–20 МБ |

### 6.2 Схема базы (SQLite)

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;

CREATE TABLE data_pack (
    id           INTEGER PRIMARY KEY,
    code         TEXT NOT NULL UNIQUE,     -- 'map-2026.11'
    version      TEXT NOT NULL,
    game_version TEXT,
    imported_at  TEXT NOT NULL,
    checksum     TEXT NOT NULL
);

CREATE TABLE marker_kind (
    id      INTEGER PRIMARY KEY,
    code    TEXT NOT NULL UNIQUE,          -- 'chest', 'ore', 'flower', 'waypoint'
    name_ru TEXT NOT NULL,
    icon    TEXT,
    color   TEXT
);

CREATE TABLE region (
    id      INTEGER PRIMARY KEY,
    code    TEXT NOT NULL UNIQUE,
    name_ru TEXT NOT NULL,
    min_x REAL, max_x REAL, min_z REAL, max_z REAL
);

CREATE TABLE layer (
    id      INTEGER PRIMARY KEY,
    code    TEXT NOT NULL UNIQUE,          -- 'surface', 'chasm_underground'
    name_ru TEXT NOT NULL
);

CREATE TABLE marker (
    id           INTEGER PRIMARY KEY,
    data_pack_id INTEGER NOT NULL REFERENCES data_pack(id) ON DELETE CASCADE,
    kind_id      INTEGER NOT NULL REFERENCES marker_kind(id),
    subtype      TEXT,
    x            REAL NOT NULL,
    z            REAL NOT NULL,
    y            REAL,
    layer_id     INTEGER NOT NULL DEFAULT 0 REFERENCES layer(id),
    region_id    INTEGER REFERENCES region(id),
    payload      TEXT                       -- JSON: редкость, группа спавна, источник
);

CREATE INDEX idx_marker_kind  ON marker(kind_id);
CREATE INDEX idx_marker_layer ON marker(layer_id);

CREATE VIRTUAL TABLE marker_rtree USING rtree(id, min_x, max_x, min_z, max_z);

CREATE TABLE marker_state (
    marker_id    INTEGER PRIMARY KEY REFERENCES marker(id) ON DELETE CASCADE,
    state        TEXT NOT NULL,             -- 'unknown' | 'collected' | 'ignored'
    collected_at TEXT,
    respawn_at   TEXT
);

CREATE TABLE display_profile (
    id          INTEGER PRIMARY KEY,
    display_key TEXT NOT NULL UNIQUE        -- '2560x1440@150%'
);

CREATE TABLE calibration (
    id                  INTEGER PRIMARY KEY,
    display_profile_id  INTEGER NOT NULL REFERENCES display_profile(id),
    minimap_cx          REAL NOT NULL,
    minimap_cy          REAL NOT NULL,
    minimap_radius      REAL NOT NULL,
    px_per_meter        REAL NOT NULL,
    north_offset_deg    REAL NOT NULL DEFAULT 0,
    rotates_with_camera INTEGER NOT NULL,
    screen_w            INTEGER NOT NULL,
    screen_h            INTEGER NOT NULL,
    hud_scale           REAL NOT NULL,
    verified_at         TEXT
);

CREATE TABLE setting (key TEXT PRIMARY KEY, value TEXT NOT NULL);
```

Запрос «объекты в радиусе»:

```sql
SELECT m.id, m.kind_id, m.x, m.z, m.y, m.layer_id,
       ((m.x - :x)*(m.x - :x) + (m.z - :z)*(m.z - :z)) AS d2
FROM marker_rtree r
JOIN marker m ON m.id = r.id
WHERE r.max_x >= :x - :r AND r.min_x <= :x + :r
  AND r.max_z >= :z - :r AND r.min_z <= :z + :r
  AND m.layer_id = :layer
ORDER BY d2
LIMIT 50;
```

### 6.3 Четыре системы координат

Это место, где чаще всего возникают ошибки, поэтому оно описано отдельно и подробно.

| Система | Единицы | Начало | Использование |
|---|---|---|---|
| **CS0 — экран** | пиксели | левый верхний угол окна | ROI, отрисовка |
| **CS1 — миникарта** | пиксели | центр круга = игрок | анализ картинки |
| **CS2 — мир** | метры | условный ноль карты | база, навигация |
| **CS3 — атлас** | пиксели тайла | левый верхний угол тайла z0 | рендер карты |

Преобразования:

```
CS0 → CS1:  p1 = (p0 - c)            где c = (cx, cy) — центр круга
CS1 → CS2:  P  = A + R(-θ) · (p1 / s)
            где s — пикселей на метр, θ — направление камеры, A — позиция игрока
CS2 → CS1:  p1 = R(θ) · (P - A) · s
CS2 → CS3:  p3 = M_zoom · P + b_zoom  (аффинно, для каждого зума своё)
```

Все преобразования выполняются **только** в `Geo.Model`. В остальных модулях нет ни одной
«магической» константы с координатами.

### 6.4 Калибровка

Калибровка привязана к профилю дисплея, потому что от разрешения и масштаба интерфейса зависят
и положение, и радиус миникарты.

Параметры: `minimap_cx`, `minimap_cy`, `minimap_radius`, `px_per_meter`, `north_offset_deg`,
`rotates_with_camera`.

Процесс калибровки:

1. **Автопоиск круга:** радиальный перепад яркости по направлениям (грубый проход по
   кадру, затем уточнение центра и радиуса). Направления за краем кадра пропускаются,
   поэтому находится и круг, обрезанный краем захвата; из близких кандидатов выбирается
   внешняя граница, а не похожая на кольцо текстура внутри.
2. **Стартовый масштаб:** обзор миникарты — около 93 м в поперечнике, поэтому
   `px/м = диаметр найденного круга / 93`. Размер квадрата захвата — только запасная
   оценка, когда круг не найден. Оценка уточняется по двум привязкам
   (телепорт или снимок карты): расстояние по одометрии сравнивается с расстоянием
   по карте, направление проверяется отдельно.
3. **Поворот:** маркер «N» на миникарте либо форма стрелки игрока.
4. **Валидация:** 30 секунд движения; сравнение с результатом релокализации; при расхождении
   более 5% — повторная калибровка.

| Слой | Выбор | Почему |
|---|---|---|
| Runtime | .NET 8 (LTS) | производительность, P/Invoke, единый язык |
| Язык | C# 12 | скорость разработки + зрелые CV-биндинги |

| Рендер | SkiaSharp + DirectComposition | 60 FPS, качественный текст и иконки |
| БД | SQLite (Microsoft.Data.Sqlite) | встроенная, WAL, rtree |
| IPC | MemoryMappedFile + MessagePack-CSharp | почти без аллокаций |

| Тесты | xUnit, BenchmarkDotNet | регрессии перф-метрик обязательны |

**Отвергнутые альтернативы и причины:**

- **Python (dxcam + OpenCV + PySide6)** — лучший вариант для прототипа CV, но GIL, упаковка и
  рендер 60 FPS проблематичны. Годится для проверки гипотез, не для финала.
- **C++ + Win32 + D2D** — максимум контроля, но втрое больше времени разработки.
- **WPF с `AllowsTransparency`** — быстрый MVP-оверлей, но layered window даёт потолок 30–40 FPS.
  Допустимый fallback, не целевое решение.
- **Electron/Tauri** — тяжёлый webview в оверлее не нужен.
- **BitBlt/GDI** — не работает с аппаратно-ускоренными окнами (чёрный кадр).

## 8. Алгоритмы

### 8.1 Захват кадра

`Windows.Graphics.Capture` с `BorderRequired = false`, получение `ID3D11Texture2D` на каждый кадр.
Кадр уменьшается до 640×640 на GPU, затем один раз копируется в память. Метка времени берётся из
`SystemRelativeTime` кадра, а не из локальных часов — это важно для корректной интерполяции.

Кадры складываются в буфер на 2 слота: если анализ не успел, старый кадр **отбрасывается**.
Очередь не должна расти: лучше потерять кадр, чем накапливать задержку.

### 8.2 Нормализация миникарты

1. ROI из калибровки (квадрат вокруг миникарты).
2. Поиск круга по радиальному перепаду яркости → центр и радиус. Направления за краем
   кадра пропускаются, поэтому находится и круг, обрезанный краем захвата.
3. Кроп квадрата, описанного вокруг круга, **без масштабирования**: пересчёт размера
   искажает субпиксельную оценку сдвига и ломает `px/м`, посчитанный по диаметру.
4. Стрелку игрока в нормализаторе не вырезаем. Чёрное пятно усиливается `CLAHE`
   и даёт статичное светлое кольцо, которое тянет корреляцию к нулю — метка замирает.
   Стрелку гасит окно корреляции трекера: плавным радиальным спадом, а не резкой
   маской, потому что резкая граница сама по себе статична.
5. Grayscale. `CLAHE` применяется в трекере уже после нормализации, чтобы выровнять
   контраст между кадрами.

Результат — `MinimapPatch`.

### 8.3 Оценка поворота

Два режима, зависящих от ответа на вопрос «вращается ли миникарта»:

- **Миникарта north-up:** `HeadingDeg` берётся из формы стрелки игрока либо из маркера «N».
- **Миникарта вращается:** угол оценивается через **логарифмически-полярное преобразование**
  (`warpPolar`) и фазовую корреляцию (`phaseCorrelate`) — это даёт поворот и масштаб за один
  проход БПФ (метод Фурье–Меллина), без перебора углов.

Оценка угла — самая чувствительная часть: ошибка в 1° на краю круга радиусом 90 px даёт смещение
около 1.5 px, что при масштабе ~2 px/м превращается в ~0.8 м ошибки на каждом шаге.

### 8.4 Одометрия

```
Δpx  = фазовая корреляция(patch[t-1], patch[t])   // окно Ханна + плавное пятно в центре
если response < 0.06 → кадр отбраковывается (нет текстуры)
Δpx  = уточнение по взвешенной невязке (SSD)      // ±1 px, бикубика, оба кадра навстречу
Δмир = R(-θ) · (Δpx / s)
```

Пик корреляции уточняется параболой, затем сдвиг ищется прямым поиском по SSD с
бикубической интерполяцией. Кадры сдвигаются навстречу друг другу на половину
смещения: если двигать только текущий кадр, интерполяция размывает его тем сильнее,
чем больше сдвиг, и SSD систематически занижает малые сдвиги. На 30 fps сдвиг за
кадр — доли пикселя, и такая ошибка съедала почти всё движение.

Одометрия подаётся в фильтр как **управляющий вход** (control input), а не как измерение: она
описывает, как должна измениться позиция, а не какой она стала.

### 8.5 Релокализация

1. Из кропа извлекаются ORB/AKAZE-дескрипторы (500–800 точек).
2. Матчинг по атласу (FLANN). Кандидаты ограничиваются кругом ±50 м вокруг текущей оценки;
   при неудаче — глобальный поиск.
3. `RANSAC` + аффинная модель → позиция, поворот, число инлайеров.
4. Fallback на «бедном» террейне (вода, песок): нормализованная кросс-корреляция по пирамиде атласа.

Результат — измерение для фильтра плюс метрика качества (число инлайеров, NCC).

#### 8.5.1 Реализованная абсолютная привязка по карте (M)

В MVP релокализация сделана не по миникарте, а по **снимку экрана карты** — так проще
и точнее: карта (M) и атлас HoYoLAB — одно и то же изображение мира.

1. Приложение сворачивается, GDI снимает клиентскую область окна игры и вырезает
   центральный квадрат (82 % меньшей стороны). Центр квадрата = маркер игрока.
2. Маска убирает рамку интерфейса и сам маркер.
3. ORB (`nFeatures ≈ площадь / 300`, до 80 000) строит индекс атласа; индекс кэшируется
   в памяти. Запрос уменьшается в 1,0 / 0,7 / … / 0,07 раза: зум карты в игре неизвестен.
4. BFMatcher: сначала ratio-тест Лоу (0,75), затем — если пар мало — взаимные ближайшие
   соседи. `EstimateAffinePartial2D` (RANSAC, 4 px) отбрасывает ложные пары.
5. **Фотометрическая проверка:** область атласа переносится в систему координат запроса,
   считается нормированная корреляция по маске. Геометрия без похожей картинки —
   почти всегда случайность, поэтому `NCC < 0,35` (0,5 для резервного пути) отвергается.
6. Два уровня: сначала текущий фрагмент нулевого зума (быстро и точно), при неудаче —
   глобальный атлас (зум −2, 4 м/пиксель, 9216×8192), затем уточнение по фрагменту
   нулевого зума вокруг найденной точки.
7. Результат отдаётся в `SnapToWorld` как измерение с честной оценкой `±м`
   (`2,5 · м/пиксель / √инлайеров`).

Почему зум −2, а не −3: на −3 пиксель равен 8 м, и снимок 900–1200 px приходится
уменьшать в 8 раз — на таких маленьких запросах ORB теряет устойчивость. На −2
масштаб отличается в 2–4 раза, и совпадение находится даже на бедном рельефе.

### 8.6 Слияние: фильтр Калмана

Состояние: `x = [X, Z, VX, VZ]`, модель равномерного движения, `Q` зависит от скорости.

- Предсказание: `x' = F·x + B·u` (u — одометрия).
- Обновление: только если `Mahalanobis(измерение) < 3σ` — защита от ложных совпадений.
- Телепорт: обнаруживается по скачку (резкое изменение сцены / экран загрузки), фильтр
  **сбрасывается**, а не сглаживает скачок.
- Смена слоя (пещера, подземелье): скрытая марковская модель по слоям; переключение модели,
  а не выброс измерения.

Уверенность считается как взвешенная комбинация: число инлайеров последней релокализации,
NCC, время с последней релокализации, согласованность одометрии и предсказания.

### 8.7 Выбор и ранжирование цели

Для показа «ближайшего объекта»:

```
score = w1 * (1 / (1 + distance)) + w2 * (1 / (1 + |bearing - heading|)) + w3 * typePriority
```

Фильтры: тип объекта, слой, «не собрано». Подсказка «выше/ниже» — по разнице `Y` с порогом
(например, ±3 м).

## 10. Критические ограничения и подводные камни

Этот раздел — концентрат того, на чём подобные проекты обычно ломаются.

### 10.1 Композитинг прозрачного окна

- `WPF AllowsTransparency` = layered window = CPU-композитинг = 30–40 FPS. Не использовать.
- Правильный путь: `WS_POPUP | WS_EX_NOREDIRECTIONBITMAP`, DirectComposition + swapchain с
  `DXGI_ALPHA_MODE_PREMULTIPLIED`, отрисовка Skia в текстуру.
- Сквозные клики: `WS_EX_TRANSPARENT | WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW`. Для интерактивных
  элементов — отдельное окно-хотспот либо `WM_NCHITTEST` → `HTCLIENT` только над элементами.

### 10.2 Эхо в захвате (самая коварная проблема)

`Windows.Graphics.Capture` захватывает **весь экран, включая ваш оверлей**. Если это не учесть,
программа увидит собственные иконки, и локализация начнёт выдавать ложные результаты.

Решение: `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` (Windows 10 2004+).
Обязателен автотест: в захваченном кадре не должно быть ни одного пикселя оверлея.

### 10.3 Режим экрана

Рисовать поверх **эксклюзивного** полноэкранного режима нельзя. Требуется borderless windowed.
Программа должна это проверять и явно сообщать пользователю, если режим неподходящий.

### 10.4 DPI и мультимониторинг

Нужен per-monitor v2 awareness, пересчёт ROI на `WM_DPICHANGED`, отдельная калибровка на каждый
профиль дисплея. Хардкод координат ломается у большинства пользователей.

### 10.5 HDR

При включённом HDR кадр приходит в другом цветовом пространстве. Без тонмаппинга компьютерное
зрение получает пересвеченную картинку, а цвета оверлея не совпадают с игрой.

### 10.6 Правовые риски

Правила HoYoverse запрещают сторонний софт, взаимодействующий с клиентом. Проект не модифицирует
игру, не читает память и не автоматизирует ввод, то есть относится к наименее инвазивному классу
инструментов, но **гарантий отсутствия блокировки нет**. Практические следствия:

- не добавлять обфускацию, скрытность, автозапуск «втихую» — это повышает подозрительность;
- распространять как локальный open-source инструмент с явным дисклеймером;
- не публиковать в репозитории датмайненые ассеты — только генератор пакета;
- тестировать на аккаунте, который не жалко.

### 10.7 Однородный террейн

Вода, песок, снег дают мало особых точек — релокализация падает. Именно поэтому одометрия
является основным контуром, а релокализация — уточняющим.

| **4. Локализация** | 2,5 нед. | нормализация, одометрия, релокализация, Калман, офлайн-стенд | медиана ≤ 3 м, p95 ≤ 8 м, `Lost` < 5% |
| **5. Интерфейс** | 2 нед. | мини-карта, указатель, индикация состояния, калибровка, настройки, трей | калибровка ≤ 2 мин, 8 из 10 задач без подсказок |
| **6. Тест и релиз** | 1,5 нед. | матрица конфигураций, тест на утечки, регрессия, установщик, документация | 8 ч без роста памяти, 20/20 запусков, установка < 5 мин |

**Итого:** 10–11 недель для одного разработчика при полной занятости.

**Критический путь:** этап 2 → этап 4 → этап 5 → этап 6. Этап 3 может идти параллельно этапу 2.

**Правило проекта:** любой этап заканчивается демонстрацией и измеримой проверкой, а не оценкой
«выглядит нормально».

### 12.1 Резервный план при провале локализации

Если к середине этапа 4 медианная ошибка превышает 10 м и нет понятного пути улучшения:

**Снап по точкам телепортации + счисление пути.** Игрок открывает карту или телепортируется;
приложение детектирует полноэкранный интерфейс карты и фиксирует точное положение известной
точки телепортации из базы; далее позиция отслеживается одометрией. Точность ±1 м сразу после
снапа, дрейф ≤ 1 м/мин.

Это честно решает исходную задачу (телепорт → дойти до ближайшего сундука), требует одного
действия от игрока и заодно подходит для подземелий.

## 14. Глоссарий

- **Маркер** — запись в базе о точке интереса: сундук, ресурс, телепорт.
- **MinimapPatch** — нормализованный фрагмент миникарты, вход локализации.
- **GeoState** — текущее состояние позиции игрока (координаты, угол, уверенность).
- **Одометрия** — оценка перемещения по смещению картинки между кадрами.
- **Релокализация** — определение абсолютной позиции сопоставлением с атласом карты.
- **Атлас** — заранее подготовленный набор тайлов полной карты мира.
- **Слой** — вертикальный уровень мира (поверхность, подземелья).
- **Пакет данных** — версионированный набор маркеров и тайлов, импортируемый в базу.
- **Эхо захвата** — попадание собственного оверлея в захватываемое изображение.
- **Click-through** — свойство окна пропускать клики в приложение под ним.
- **CLAHE** — адаптивное выравнивание локального контраста, применяется к миникарте.
- **WGC** — Windows Graphics Capture.
- **DComp** — DirectComposition.

## 15. Чек-лист для продолжения работы

1. Прочитать §13 (открытые вопросы) и закрыть Q1–Q4 записью сессий. **Без этого реализацию
   локализации начинать нельзя.**
2. Развернуть каркас решения по §9, собрать и прогнать тесты на чистой машине.
3. Реализовать `Capture.Service` + `Overlay.Presenter` (этап 2) — это проверка жизнеспособности
   всего подхода. Если 60 FPS и отсутствие эха не достигаются, дальше идти нет смысла.
4. Написать `SessionRecorder` и записать датасет с эталонными координатами — без него невозможно
   измерить качество локализации.
5. Реализовать локализацию по §8 и прогнать на датасете. Сравнивать с порогами из §11.
6. Только после этого — база данных, интерфейс, полировка.

**Что нельзя делать ни при каких условиях:** инъекция в процесс игры, чтение памяти, хукинг
графического API, эмуляция ввода, обфускация и сокрытие работы программы. Это и технически
сложнее, и является прямым нарушением правил игры.
